# FOOTSIES in C/CUDA

A byte-identical port of the FOOTSIES game and environment to plain C
functions that compile for both the CPU and CUDA. It is ported from the JAX
replica (`footsiesgym/jax`), which is validated against the Unity game: the
operation order of every float computation comes from the JAX port, and the
control flow (early returns, in-place updates) from the C#.

```
csrc/
  footsies.h          state structs, constants, every game + env function (host and device)
  footsies_batch.h    SIMD batches for the CPU: 16 games per block, struct-of-arrays, branch-free
  footsies_avx512.h   the AVX-512 frame and env step for those blocks
  frame_data.gen.h    generated by scripts/gen_c_frame_data.py from footsiesgym/jax/frame_data.py
  footsies_cpu.c      batched CPU entry points (OpenMP), loaded with ctypes
  bench_native.c      single-thread throughput without Python
  footsies_ffi_cpu.cc XLA FFI handlers on the host
  footsies_cuda.cu    kernels, a C API on device pointers, XLA FFI handlers on the GPU
```

Python bindings live in `footsiesgym/c`, which compiles these on first use
(cached in `~/.cache/footsiesgym`):

| | |
|---|---|
| `CGames` | batches of `BattleSimulation`s stepped frame by frame (interface of `JaxReplay`) |
| `FootsiesCEnv` | `FootsiesJaxEnv`'s environment, batched, on numpy arrays (SIMD + OpenMP) |
| `FootsiesFFIEnv` | the same environment as an XLA FFI call, with `FootsiesJaxEnv`'s functional API |
| `cuda.CudaEnv` | the CUDA kernel through its C API (tests and benchmarks) |

```python
from footsiesgym.c import FootsiesCEnv, FootsiesFFIEnv

env = FootsiesCEnv(num_envs=4096, frame_skip=4, action_delay=8)
obs = env.reset()                                    # {"p1": (4096, 88), "p2": ...}
obs, rewards, terminateds, truncateds = env.step(actions)   # actions: (4096, 2)

env = FootsiesFFIEnv(frame_skip=4).vectorize(4096)   # drop-in for FootsiesJaxEnv(...).vectorize
obs, state, infos = jax.jit(env.reset)(key)
obs, state, rewards, terminateds, truncateds, infos = jax.jit(env.step)(key, state, actions)
```

`FootsiesFFIEnv` runs the CUDA kernel when JAX has a GPU (building
`footsies_cuda.cu` with `nvcc`, found from `$NVCC`, `$CUDA_HOME` or `PATH`)
and the OpenMP loop otherwise. Its state is an opaque
`uint8[num_envs, sizeof(EnvState)]` buffer, updated in place when donated;
`state.t` and `state.episode_id` read like the JAX port's.

## CPU batching

`FootsiesCEnv` (`impl="batch"`, the default) steps games in blocks of 16,
one game per 32-bit SIMD lane:

- **State** is struct-of-arrays (`EnvBlock`: one 64-byte row of 16 lanes per
  field), allocated once, 64-byte aligned. Output buffers are preallocated
  and aligned too; `step` allocates nothing.
- **Control flow** is branch-free: the C#'s early returns become per-lane
  masks, and "first active entry" scans become fixed-length loops. The
  portable form (`footsies_batch.h`) is per-lane C that compilers vectorize.
- **AVX-512** (`footsies_avx512.h`, used when the compiler targets it):
  table lookups are register permutes (`vpermi2d`, tables of at most 32
  entries) instead of gathers; requests, hits and dash checks that no lane
  needs are skipped; the frameskip runs on registers; observations are
  written with a 16x16 register transpose.
- The library is built with `-march=native` (override with
  `FOOTSIES_MARCH`); the build cache is keyed on the CPU's feature flags.

Measured on a 2.1 GHz Xeon (Sapphire Rapids) with frame skip 4 and random
actions, through Python (`benchmarking/bench_c_throughput.py`):

| | 1 core | 4 cores |
|---|---|---|
| `impl="scalar"` | ~1.8M env-steps/s | |
| `impl="batch"` (AVX-512) | ~6-6.6M env-steps/s (1k-16k envs) | ~20M env-steps/s |

Above about 16k envs per core, state and observations stop fitting in cache
and throughput becomes memory-bound (3.7M/s per core at 65k envs).

The float operations are the same IEEE operations in the same order as
`footsies.h`, so the batches are byte-identical to it; the tests compare
state, observations, rewards and done flags after every step, for the
AVX-512, portable and AVX2 builds.

## Byte identity

The compiler flags are part of the spec:

- **gcc/clang:** `-O3 -ffp-contract=off`. Never `-ffast-math` or `-Ofast`
  (`footsies.h` refuses to compile with them). GCC contracts `a*b+c` into an
  FMA by default when the target has one (`-march=native`).
- **nvcc:** `-fmad=false -prec-div=true -ftz=false`. Never `--use_fast_math`.
  nvcc fuses `a*b+c` into an FMA by default.

Float semantics:

- A single float32 `+ - * /` is ported as the same C operation, in the
  JAX port's order. Mono evaluates float expressions in double, but for one
  operation on two floats, rounding to double then to float equals rounding
  once.
- Movement is the expression Mono evaluates, `(float)((double)pos +
  (double)(speed * sign) * (double)FIXED_DELTA_TIME)`, where JAX needs an
  error-free float32 emulation.
- The encoder divides directly (`(float)k / 25.0f`): IEEE division is
  correctly rounded on the CPU and on CUDA with `-prec-div=true`. JAX uses
  lookup tables because XLA's float32 division isn't.
- Frame data floats are emitted as hex literals.

Structs have no implicit padding (static asserts), so CPU and CUDA states
can be compared with `memcmp`.

One difference from the Unity vectorized server is kept on purpose, as in
the JAX port: an env-level reset starts a completely fresh game, while Unity
carries hit stun, frame advantage and the proximity-guard flags across
episodes.

## Validation

`testing/test_c_backend.py`:

1. **Movement** against numpy float64 for float32 positions in [-8, 8]
   (strided by default; every position with `FOOTSIES_LONG_TESTS=1`).
2. **Unity trace** (`testing/data/unity_trace_9c6b36f.npz`, 6,000 frames x 16
   games, every `BatchRawState` field): the bar for byte-identical.
3. **JAX port**, every raw field after every frame with sticky random
   inputs, and the env level (observations, rewards, terminated, truncated,
   `t`, `episode_id`) with action delay, special charge, KOs, truncation and
   resets, both through `FootsiesCEnv` and the FFI call.
4. **Builds agree byte for byte**: gcc, clang and `-march=native` on the
   CPU, and the CUDA build against the CPU build (`memcmp` of the states
   after every step; skipped without a GPU).

Larger runs:

```bash
python -m footsiesgym.c.validation trace
python -m footsiesgym.c.validation jax --num-envs 4096 --frames 100000
FOOTSIES_LONG_TESTS=1 pytest testing/test_c_backend.py
```

## Regenerating the frame data

```bash
python scripts/gen_c_frame_data.py          # rewrite csrc/frame_data.gen.h
python scripts/gen_c_frame_data.py --check  # fail if it is out of date
```

The generator expands its sparse ranges back into dense tables and checks
them against `footsiesgym.jax.frame_data.FRAME_DATA` bit for bit before
writing.

## GPU notes

- The whole frameskip runs in registers: every kernel compiles to
  "0 bytes stack frame" (check with `nvcc -Xptxas -v`). Arrays that are
  indexed at runtime would move the state to local memory, so small loops
  are unrolled and the action-delay queue is scanned with constant indices.
- The frame tables (about 1.8 KB) are copied into shared memory once per
  block, not `__constant__`: warps hold different actions, and constant
  memory serializes reads of different addresses.
- The env-step kernel uses about 234 registers per thread, which limits
  occupancy. Profile on hardware before tuning
  (`__launch_bounds__(256, 2)` would cap it at 128 registers).
- Observation writes (704 bytes per env step) are probably the main memory
  cost. If Nsight Compute shows poor store efficiency, stage them in shared
  memory and write them coalesced.
